## 1. Key finding — NTFS bash-mount stale view (critical workflow hazard)

### What was observed

When ruff and `wc -l` were invoked via the bash sandbox on the NTFS mount,
they reported 9–12 files with syntax errors (truncated mid-expression):

| File (bash view) | bash `wc -l` | Actual (Read tool) | Δ |
|---|---:|---:|---:|
| `resilient_updates/cli.py` | 790 | 890 | +100 |
| `resilient_updates/enrichment.py` | 197 | 301 | +104 |
| `resilient_updates/healthcheck.py` | 109 | 124 | +15 |
| `resilient_updates/reporting.py` | 538 | 551 | +13 |
| `resilient_updates/scan.py` | 96 | 179 | +83 |
| `resilient_updates/scanner_diff.py` | 351 | 357 | +6 |
| `resilient_updates/vex.py` | 160 | 167 | +7 |
| `tests/test_cli.py` | 246 | 316 | +70 |
| `tests/test_enrichment.py` | 123 | 207 | +84 |
| `tests/test_reporting.py` | 76 | 122 | +46 |
| `tests/test_vex.py` | 263 | 263 | 0 |
| `tests/test_reporting_helpers.py` | 311 | 312 | +1 |

**Root cause:** The NTFS FUSE mount caches file content.  New bytes written on
the Windows side are invisible to bash until the cache is invalidated.  This
is the same issue noted in project memory and `docs/audit/140-fixups-2026-06-01d.md`.

**All source files are syntactically complete** when read via the Windows
filesystem path.  No source code is actually broken.

### Impact

- Any automated tool that runs via the bash mount (ruff, pytest, wc) will
  produce **false positives** on recently-written files until the mount cache
  expires.  CI runs on GitHub Actions (bare Linux checkout) are unaffected.
- Developer experience: false ruff/pytest errors in the bash sandbox mislead
  automated analysis passes like this one.

### Remediation

Carry-forward from earlier audits — no change from host side:

1. Use `PYTHONPATH=. PYTHONDONTWRITEBYTECODE=1 python3 -m pytest` **after**
   copying files to `/tmp` (or run directly from Windows PowerShell).
2. The `make test` target is correct for Windows-side dev; it does not use
   the bash mount.
3. For automated analysis sessions: prefer the Read tool over bash cat/wc to
   inspect actual file state.

## 5. Architecture, test, documentation and tooling findings

### 5.1 `_normalize_severity` duplicated (known P4 carry-forward)

Defined identically in both `reporting.py` and `scanner_diff.py`.  Neither
module imports from the other.  Both definitions are stable and consistent,
but the duplication means a future change must be made in two places.

**Recommended fix:** move the canonical implementation to `resilient_updates/_io.py`
(already the shared utility module for `sha256_*`, `read_json`, etc.) and
import from there in both modules.

### 5.2 `requirements.lock` is still a placeholder

The file mirrors `requirements.txt` loose constraints rather than a
pip-compiled hashed lockfile.  CI installs from `requirements.txt` (also
loose).  Docker builds are therefore not fully reproducible.

**Recommended fix:**
```
pip install "pip-tools>=7.4"
make lock   # -> pip-compile --strip-extras --generate-hashes
```
Commit both `requirements.in` and the updated `requirements.txt` and
`requirements.lock`.

### 5.3 `.git/index.lock` present on host

A stale `index.lock` file prevents git operations from the bash mount
(`git checkout --`, `git add`, `git commit`).

**Fix from Windows PowerShell:**
```powershell
Remove-Item .git\index.lock -Force
```

### 5.4 `docs/audit/110-140` and `test_reporting_helpers.py` not committed

Four audit files and the 38-test helper suite exist only in the working tree.
If the working tree were reset, this work would be lost.

**Recommended fix:**
```bash
git add docs/audit/110-fixups-2026-06-01.md \
        docs/audit/120-fixups-2026-06-01b.md \
        docs/audit/130-fixups-2026-06-01c.md \
        docs/audit/140-fixups-2026-06-01d.md \
        tests/test_reporting_helpers.py
git commit -m "chore(audit): commit 2026-06-01 audit docs and reporting helper tests"
```

### 5.5 CI pytest job uses `--maxfail=1`

`.github/workflows/ci.yml` `pytest` job has `--maxfail=1` which stops the
suite at the first failure and hides subsequent failures.  The `Makefile`
`test` target was already fixed to remove `--maxfail=1` (audit 140), but CI
still has it.

**Recommended fix:** remove `--maxfail=1` from the pytest step in ci.yml.

### 5.6 ADR-0005 P2 `run_scan` not tested for failure propagation

`scan.py` `run_scan` stops at the first failed step (`break`), but
`test_scan.py` doesn't have a test verifying that subsequent steps are
skipped on failure.

**Recommended fix:** add a test that injects a failing runner on step N and
asserts that step N+1 is absent from `result["steps"]`.

### 5.7 NVD API keys — rotation carry-forward (host)

From previous audits: NVD API keys should be rotated.  No automated action
possible from this session.
