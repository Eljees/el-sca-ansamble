### NEW-2 — `versions.env` создан, частично подключён, хвост sidecar-ов в хардкоде (P1)

**Поправка после внимательной перепроверки**: я был неправ при первичной grep-выборке.  В `docker-compose.yml` уже используются переменные для основных сканеров:

```
41:  image: aquasec/trivy:${TRIVY_VERSION:-0.64.1}
63:  image: aquasec/trivy:${TRIVY_VERSION:-0.64.1}
105: image: ghcr.io/anchore/grype:${GRYPE_VERSION:-v0.112.0}
139: image: ghcr.io/anchore/grype:${GRYPE_VERSION:-v0.112.0}
160: image: ghcr.io/anchore/syft:${SYFT_VERSION:-v1.20.0}
```

…но НЕ для sidecar / Dockerfile-build версий, которые тоже объявлены в `versions.env`:

```
389: image: ghcr.io/google/osv-scanner:latest          ← нужно ${OSV_SCANNER_VERSION:-latest}
427: image: ghcr.io/xtls/xray-core:latest              ← нужно ${XRAY_VERSION:-latest}
447: image: kalaksi/tinyproxy:1.11.2                   ← нужно ${TINYPROXY_VERSION:-1.11.2}
472: image: linuxserver/wireguard:latest               ← нужно ${WIREGUARD_VERSION:-latest}
Dockerfile.cve-bin-tool: pip install ... cve-bin-tool==3.4   ← нужно ARG CVE_BIN_TOOL_VERSION
```

То есть «single source of truth» дотянут до 5 из 10 image-строк; четыре sidecar-а и pin для cve-bin-tool остаются дрейфом.

**Действие**: заменить 4 sidecar-строки в `docker-compose.yml` на `${…_VERSION:-…}`; в `Dockerfile.cve-bin-tool` добавить `ARG CVE_BIN_TOOL_VERSION=3.4`, в compose для `cve-bin-tool-*` сервисов прокинуть `build.args.CVE_BIN_TOOL_VERSION: ${CVE_BIN_TOOL_VERSION:-3.4}`.

### NEW-3 — `requirements.lock` — **placeholder**, а не настоящий lockfile (P1)

Файл в репозитории буквально написан:

> «This is a placeholder.  The actual lockfile is produced by `make lock`
> (pip-compile --strip-extras --generate-hashes ...).  Until that runs,
> this file simply mirrors requirements.txt»

Содержит `PyYAML>=6.0`, `requests>=2.31.0`, `PySocks>=1.7.1`, `pytest>=8.0.0` — нет ни одной точной версии, нет ни одного хеша.

CI ветка `if [ -f requirements.lock ]; then pip install -r requirements.lock` теперь активна — и подтягивает latest точно так же, как `requirements.txt`.  Гарантии воспроизводимости нет, хотя название говорит обратное.

**Действие**: выполнить `make lock` на хосте (`pip-compile --strip-extras --generate-hashes`), закоммитить настоящий lockfile.  До этого либо удалить placeholder, либо переименовать в `.example`.

…и зафиксировать число (например, в `docs/audit/30-tests.md` приписать «coverage baseline 2026-05-25: NN %»).  Если меньше 75 — временно поставить gate в `60` (или сколько окажется), и в отдельной заметке зафиксировать долг «дотянуть до 75».

### NEW-7 — `.git/index.lock` predicament в Linux-sandbox (P3, информационно)

`git status` в моём sandbox выдаёт:

```
warning: unable to unlink '.git/index.lock': Operation not permitted
```

Сам файл `.git/index.lock` не присутствует (`ls -la .git/index.lock` → No such file).  Это поведение Linux git, когда подложка — Windows-mount без полноценного `unlink()`.  На самой Windows никакой проблемы нет.

**Действие**: ничего.  Если на Windows-хосте `git status` отрабатывает без подобной строки — игнорируем.  Если когда-то снова появится реальный `.git/index.lock` — `Remove-Item .git\index.lock` в PowerShell.
