## 2. Changes applied this pass

### 2.1  `Dockerfile.apk-analyzer` — configurable JVM heap (§18)

**Problem.** `JAVA_TOOL_OPTIONS="-Xmx512m"` was a hardcoded `ENV` directive.
Memory-constrained or high-throughput deployments (many parallel APK scans)
had no way to adjust the JVM heap without rebuilding from a modified
Dockerfile.

**Fix.** Added `ARG JAVA_XMX=512m` before the `ENV` block; `JAVA_TOOL_OPTIONS`
now reads `"-Xmx${JAVA_XMX}"`.  Default behaviour is unchanged (512 MB).

Override at build time:
```sh
docker compose build --build-arg JAVA_XMX=1g apk-analyzer
```
Or via `.env` / `versions.env`:
```
JAVA_XMX=1g
```
`docker-compose.yml` `apk-analyzer.build.args` wired accordingly:
```yaml
args:
  JAVA_XMX: ${JAVA_XMX:-512m}
```

### 2.2  `resilient_updates/cli.py` — accumulate retry counts (§15)

**Problem.** `_dedup_attempted_sources` used `last-wins` dict semantics
(`seen[item.source.name] = item.source.to_dict()`).  When the retry loop in
`attempt_sources` produced multiple `AttemptResult` entries for the same URL
(each retry appends one), the dedup function discarded all but the last.
The output JSON reported only the final attempt, giving no visibility into
how many retries were made and what failed.

**Fix.** The function now:
- Preserves insertion order (first encounter wins for source metadata).
- Accumulates `retry_count` — total attempts against that source name.
- Sets `succeeded = True` if *any* attempt succeeded.
- Appends each attempt's `{success, reason, message, status_code}` to an
  `outcomes` list.

Sample output for a source that failed twice then succeeded:
```json
{
  "name": "primary-mirror",
  "url": "https://example.com/grype-db.tar.gz",
  "retry_count": 3,
  "succeeded": true,
  "outcomes": [
    {"success": false, "reason": "http_5xx", "message": "http status 503", "status_code": 503},
    {"success": false, "reason": "http_5xx", "message": "http status 503", "status_code": 503},
    {"success": true,  "reason": null,        "message": "ok",              "status_code": 200}
  ]
}
```

Callers of `_dedup_attempted_sources` (three call sites in `cli.py`) are
unchanged — they pass `list[AttemptResult]` and receive `list[dict]` as
before.  The extra keys are additive and do not break existing downstream
consumers of `artifacts/provenance/*.json`.

## 4. Pass 2 additions (same day, continued run)

### 4.1  `resilient_updates/atomic_publish.py` — EXDEV staging on dst volume (§13)

**Problem.** The EXDEV fallback in `_replace_tree` did `rmtree(dst) →
copytree(src, dst) → rmtree(src)`.  Two issues:

- If `copytree` failed mid-way, `dst` was already removed with no rollback.
- The `dst`-absent window lasted for the entire copy duration rather than
  a single rename syscall.

**Fix.** On EXDEV, copy into a sibling staging path (`dst.parent/
.staging_<name>_<pid>`), then rename staging → dst (intra-volume, atomic).
If the copy fails the staging directory is cleaned up and `dst` is untouched.
The "absent window" is now a single `Path.replace()` call.

New test `test_replace_tree_exdev_cleans_staging_on_copy_failure` verifies
that a failed copy leaves no orphaned staging dirs and does not corrupt `dst`.

New smoke test `test_atomic_publish_no_active_dir` covers the first-run path
(no pre-existing active directory).

### 4.2  CI — `smoke` job added (§30-tests §3)

Added a `smoke` job to `.github/workflows/ci.yml` that runs `pytest -m smoke`
