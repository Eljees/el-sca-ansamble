## 0. Структура проекта — краткое резюме

```
el-sca-ansamble/
├── resilient_updates/        Python-оркестратор (CLI, fallback, provenance, audit, extractor)
│   ├── cli.py                ~550 строк — все команды CLI и логика update_grype
│   ├── config.py             загрузка YAML + валидация + parse_proxy_config
│   ├── fallback.py           build_session, attempt_sources, классификация ошибок
│   ├── reporting.py          сборка итогового Markdown   ⚠️ обрезан → SyntaxError
│   ├── cve_db_audit.py       аудит DB cve-bin-tool, активация по policy
│   └── …                     atomic_publish, artifact_store, healthcheck, provenance, source_policy, extractor
├── configs/feed_sources.yaml YAML-источники (trivy, grype, cve_bin_tool, syft, proxy, custom_sources)
├── docker-compose.yml        14 сервисов; ⚠️ нет volumes:/networks:, нет apk/win-analyzer сервисов
├── Dockerfile.*              5 образов; ⚠️ Dockerfile.apk-analyzer обрезан после `RUN pip`
├── scripts/                  Linux .sh runners (run-scan.sh, scan_archive.sh, update_*.sh, collect_reports.sh, …)
│   └── windows/              PowerShell-эквиваленты (run-scan.ps1, update-*.ps1, smoke-test.ps1, …)
├── tests/                    27 тест-функций, ~1600 строк; ⚠️ часть удалена в git, осталась только на диске
├── docs/                     architecture / proxy / failure-modes / status-and-roadmap / operations …
├── artifacts/                output: sbom, reports, provenance, mirror, extracted, cache
└── README.md, DEPLOYMENT_GUIDE_FINAL.md, CHANGES_v3.0.md
```

Архитектурный принцип проекта — **wrapper-first**: upstream-образы сканеров не модифицируются, отказоустойчивость, retry, валидация checksum/age и provenance вынесены в `resilient_updates`.

## 2. Недостатки архитектуры, тестов, доков, tooling и workflow

### 2.1. Архитектура

1. **Отсутствует слой сетевого abstract'а.** Прокси сейчас «двухслойный без середины»: переменные окружения через `x-proxy-env` (Docker) и `parse_proxy_config()` (Python). Нет per-source override, нет priority-listа прокси, нет fallback с одного прокси на другой, нет VPN-шага. Любые «множественные прокси» сегодня требуют ручного редактирования `.env` и пересборки.
2. **Нет единого entry point.** Пользователь выбирает между `run-scan.sh`, `scan_archive.sh`, `run_scan.sh`, `windows/run-scan.ps1`, набором `update-*.sh`. Поведение немного разное.
3. **Версии и компоненты разнесены.** Версии образов прибиты в compose, версии Python-зависимостей — в `requirements.txt`, версии PowerShell-скриптов — нигде. Нет общего `versions.env` / `.tool-versions`.
4. **Конфигурация `feed_sources.yaml` смешивает policy и connectivity.** В одном файле — приоритеты источников + retry policy + proxy + audit policy. Это работает на masштабе MVP, но при появлении ≥3 прокси/2 регионов файл станет нечитаем.
5. **Provenance пишется по плоской схеме.** Нет общего `MANIFEST.json`, который ссылался бы на отдельные `provenance/*.json`, `extraction_manifest.json`, `summary.json`, `status.json` с timestamp run-id; trace по одному запуску собирается из шести разных файлов.
6. **Нет наблюдения runtime-стека.** Логи контейнеров остаются в `docker logs` и `artifacts/reports/cve-bin-tool/attempts/`. Никакого структурированного `events.jsonl`.
7. **`atomic_publish.publish_directory()` на Windows** уже имеет fallback через `shutil.copytree` (см. `cve_db_audit.activate_best_cve_bin_tool_db`), но не атомарен: между удалением active и rename'ом существует окно. Для cve-bin-tool DB ~ 6 ГБ это секунды, и за это окно scanner может прочитать пустой каталог.

### 2.2. Тесты

1. Нет CI: pytest никем не запускается системно.
2. Покрытие функций неравномерное: `fallback.py` — 6 тестов, `proxy.py` — 16, а целые модули (`extractor.py`, `cve_db_audit.py`, `cli.py`, `atomic_publish.py`) покрыты 1–3 тестами каждый.
3. Нет integration-тестов на `docker compose`. `mock-feed-server` есть, но запускается вручную.
4. `pytest --cov` не настроен, coverage-цель не зафиксирована.
5. Тесты на git-уровне частично удалены (см. P0-6) — фактическое и трекаемое состояние расходятся.

### 2.3. Документация

1. Семь документов в `docs/` + три на верхнем уровне; нет sitemap'a — какой документ за что отвечает.
2. `docs/status-and-roadmap.md` — самостоятельный мини-changelog, дублирующий `CHANGES_v3.0.md`.
3. Нет `CHANGELOG.md` (semver-формат).
4. Нет руководства разработчика (как добавить тест, как локально собрать без интернета, как добавить новый источник).
5. `docs/proxy.md` — самый сильный документ в репо (10+ KB), но описывает только сегодняшнюю модель, не цепочки.
6. Нет ADR (`docs/adr/0001-wrapper-first.md`, `0002-proxy-sidecar.md`) — все решения растворены в комментариях кода.

### 2.4. Tooling

1. Нет линтеров (`ruff`, `mypy`, `shellcheck`, `hadolint`, `yamllint`).
2. Нет pre-commit hook'ов.
3. Нет Makefile / `just` / `task` — общие команды переписаны в `run-scan.sh` и `run-scan.ps1`.
4. `requirements.lock` отсутствует; `pip-tools` / `uv pip compile` не используются.
5. Docker build-cache не настроен (нет `BUILDKIT_INLINE_CACHE`, нет `--cache-from`).
6. Нет `docker-bake.hcl` — образы пересобираются по одному.

### 2.5. Workflow

1. `git index.lock` лежит несколько дней — никаких pre-commit guard'ов нет.
2. Нет PR-шаблона, нет review-конвенций.
3. Сборка артефактов и публикация образов делается на одной машине; нет reproducible builds.
4. Нет release-процесса (`make release` → tag → build images → push).

## 3. Как устранять — общие принципы

Все правки делятся на пять классов; для каждого фиксируется acceptance criteria.

1. **P0 hot-fix bundle** (синтаксис + compose). Прохождение: `python -m py_compile resilient_updates/*.py` → ok; `docker compose config -q` → ok; `docker compose build` → ok.
2. **P1 поведенческие исправления**. Прохождение: pytest + сценарные smoke-тесты.
3. **Network/proxy/VPN-слой**. Прохождение: scan через цепочку `tinyproxy → xray → upstream` успешно скачивает Grype DB и Trivy DB; имитация падения одного звена → fallback на другое; `healthcheck` сообщает actual statuses.
4. **Windows-оптимизация**. Прохождение: повторный full scan того же артефакта быстрее baseline на ≥40 % (целевое значение фиксируем после первого замера).
5. **Фичи и улучшения**. Прохождение: каждый item имеет отдельную проверку в плане ниже.

```
   grype-       │   front; единый      VLESS/Shadowsocks/     │                         │
   updater,     │   ALL_PROXY)         outbound rules         │                         │
   cve-bin-     │                                            │                         │
   tool-                                                     │                         │
   updater,                                                  │                         │
   syft-sbom,                                                ▼                         │
   resilient-                                          (опц.) wg0:wireguard            │
   updater)                                                  │                         │
                │                                            ▼                         │
                │                                       Internet endpoint              │
                └───────────────────────────────────────────────────────────────────────┘
```

**Почему именно так.**

- `tinyproxy` даёт единый HTTP/HTTPS-front для контейнеров, которые умеют только `HTTP_PROXY`/`HTTPS_PROXY` (Go-net/http в Trivy/Grype/Syft честно читает только http(s)).
- `xray-client` транслирует HTTP в SOCKS5h и далее в любую outbound-схему (VLESS/Shadowsocks/Trojan/SOCKS upstream). Цепочка серверов настраивается в его `config.json` через `outbounds[].streamSettings`.
- Внутри `scanner-net` сканеры обращаются по DNS-имени `http://tinyproxy:8888` — больше нет проблемы `127.0.0.1 vs host.docker.internal`.
- WireGuard sidecar (опционально, профиль `vpn`) включается, когда конечные зеркала доступны только из VPN. Сетевая модель — `network_mode: "service:wireguard"` для тех сканеров, которые должны идти не через HTTP-прокси.

`x-proxy-env` меняется так, чтобы по умолчанию указывать **на sidecar**:

```yaml
x-proxy-env: &proxy-env
  HTTP_PROXY:  ${HTTP_PROXY:-http://tinyproxy:8888}
  HTTPS_PROXY: ${HTTPS_PROXY:-http://tinyproxy:8888}
```

Чтобы оставить возможность работать через `host.docker.internal` без sidecar'a, `tinyproxy.conf` принимает upstream через переменную окружения (`Upstream socks5 host.docker.internal:1080`).

Расширяем секцию `proxy:`:


`source_policy.build_sources()` дополнительно возвращает атрибут `chain`, `attempt_sources()` использует его при инициализации `requests.Session`.

### 5.4. Новый модуль `resilient_updates/proxy_chain.py`

API:

```python
class ProxyChain:
    name: str
    hops: list[Hop]               # role, url/interface
    def healthcheck(self) -> dict # url, latency_ms, status
    def make_session(self) -> requests.Session

class ProxyRouter:
    def __init__(self, config: dict): ...
    def session_for_source(self, source: SourceCandidate) -> tuple[requests.Session, str]
    def healthcheck_all(self) -> dict[str, dict]
    def write_provenance(self, path: Path) -> None
```

CLI:

```
python -m resilient_updates.cli proxy-status      # печатает таблицу здоровья
python -m resilient_updates.cli proxy-set corp    # переключает default_chain
```

Provenance файла `artifacts/provenance/proxy.json`:

```json
{
  "default_chain": "corp",
  "chains": {
    "corp":    {"status": "ok",   "latency_ms": 184, "checked_at_utc": "..."},
    "via-vpn": {"status": "down", "error": "wg0 not up"},
    "direct":  {"status": "ok",   "latency_ms": 4012}
  },
  "selected_per_source": {"anchore-public-db": "corp", "primary-mirror": "via-vpn"}
}
```

### 5.5. Failover-логика

1. Перед каждым `attempt_sources` вызывается `ProxyRouter.session_for_source(source)`.
2. Если соответствующая цепочка нездорова — берётся следующая в `failover_order`.
3. Каждый attempt в `provenance` пишется с полем `via_chain`.
4. Healthcheck цепочек выполняется лениво (TTL 60 сек) и кэшируется в process-level singleton.

### 5.6. Безопасность

- Все upstream-секреты (Xray UUID, WG private key, NVD API key) читаются только из `.env` / Docker secrets, не из YAML.
- Логи `tinyproxy` и `xray` пишутся с маскированием URL (`LogLevel: Info`, `LogFilter` исключает `Authorization`).
- В `docs/security-notes.md` фиксируется threat-model: что произойдёт при компрометации одного звена цепочки.

## 6. Windows + WSL2 — оптимизация скорости сканирования

### 6.1. Профиль проблемы

Замеры из открытых источников и характер пайплайна позволяют выделить три источника тормозов на Windows:

1. **Defender real-time scan** проходит по каждому файлу, который extractor / scanner трогает в `artifacts/extracted/...` и в Docker VHD; на больших артефактах это ×3–×8 по wall-clock.
2. **9P bind-mount Windows → Linux container** (через `\\wsl$`/`\\.\pipe\docker_engine`): расширенные атрибуты, fsync, mtime — каждое обращение делает сетевой round-trip. Для extractor'а (`os.path.normpath`-helper уже есть) и для cve-bin-tool это десятки тысяч stat() в секунду.
3. **NTFS** медленнее ext4 на каталогах с большим числом мелких файлов (распакованные APK, npm-tree).

### 6.2. План оптимизации

1. **Defender exclusions** (`scripts/windows/setup-defender-exclusions.ps1`):
  - папка проекта (Windows path) + `D:\dev\el-sca-ansamble\artifacts\`,
   - `%LOCALAPPDATA%\Docker\wsl\data\ext4.vhdx`,
   - `%LOCALAPPDATA%\Docker\wsl\distro\ext4.vhdx`,
   - процессы `com.docker.backend.exe`, `wsl.exe`, `vmmemWSL`.
   - Скрипт идемпотентен (`Get-MpPreference` + `Add-MpPreference -Force`); пишет провенанс в `artifacts/provenance/defender.json`.

2. **Перенос горячих путей внутрь WSL ext4.** В `docker-compose.windows.override.yml`:
   ```yaml
   volumes:
     scan-cache:
       driver: local
       driver_opts:
         type: none
         o: bind
         device: /opt/sca-cache    # путь внутри WSL Ubuntu
   services:
     artifact-extractor:
       volumes:
         - scan-cache:/workspace/artifacts/extracted
   ```
   `setup-cowork.ps1` создаёт `\\wsl$\Ubuntu\opt\sca-cache` при первом запуске.

3. **BuildKit + кэш**:
   - `# syntax=docker/dockerfile:1.7` в каждом Dockerfile,
   - `RUN --mount=type=cache,target=/root/.cache/pip pip install ...`,
   - `docker buildx bake --set "*.cache-from=type=local,src=.docker-cache"` в `Makefile`/`build.ps1`.

4. **Параллелизм cve-bin-tool**: добавить флаг `-n $(nproc)` в `scripts/update_cve_bin_tool.sh` (для scan-mode), параметризовать через `CVE_BIN_TOOL_PARALLEL` (default = ½ ядер).

5. **Pre-filter в extractor.py**:
   - Конфигурируемый allow-list `extract_filter` в `feed_sources.yaml`:
     ```yaml
     extractor:
       skip_extensions: [".png", ".jpg", ".webp", ".mp3", ".woff2", ".ttf", ".doc", ".docx"]
       max_member_size_mb: 200
     ```
   - В `_extract_zip` / `_extract_tar` дополнительно фильтровать членов; счётчик skipped + причина в `extraction_manifest.json`.

6. **tmpfs для staging** (Linux/WSL):
   ```yaml
     artifact-extractor:
       tmpfs:
         - /workspace/artifacts/extracted/.tmp:size=4G
   ```
   Финальный rename — на постоянный том.

7. **`docker compose run --rm` → `docker compose up -d` + `exec`** для повторных запусков. Один long-running контейнер `db-admin` сокращает старт на 1.5–2 с/команду.

8. **Использовать `--platform=linux/amd64`** где явно: исключает повторные image-pull под WSL.

### 6.3. Замеры и acceptance

- `scripts/windows/benchmark.ps1`: трижды прогоняет full scan на reference-артефакте (Prometheus tar.gz + Win MSI), пишет `artifacts/provenance/benchmark.json`.
- Целевой эффект (предварительно, уточнить после baseline): −40 % wall-clock и −60 % CPU на secondary runs.
