### 2.2 Stale `.git/*.lock*` files — compounding suffix problem (P1, carry-forward)

The previous automated passes tried to clean up lock files but the sandbox
cannot safely delete NTFS-mounted files — so the cleanup script kept
appending suffixes (`.gone`, `.gone2`, `.stale`) to the existing
`.lock.gone.*` names. The result is files like:

```
.git/HEAD.lock.gone.gone2.gone.gone.gone.gone2.gone.gone2.gone
.git/index.lock.bak.gone1779958063.313827.rm.stale...
```

These are all zero-byte (harmless), but they clutter the git directory
and will confuse `git fsck`. The cleanup must happen on the Windows host.

**Action required (Windows PowerShell, safe when no git process is running):**
```powershell
Get-ChildItem .git -Recurse -Filter "*.lock*" | Remove-Item -Force
```
This removes every file whose name contains `.lock` — including the
accumulated `.gone`-suffixed copies. Check first with `-WhatIf`.

### 2.3 `requirements.lock` placeholder — no pinned hashes (P1, carry-forward)

`requirements.lock` is still a 14-line stub that mirrors `requirements.txt`
without hashes. CI installs from it as a fallback when it exists:

```yaml
if [ -f requirements.lock ]; then
  pip install -r requirements.lock
else
  pip install -r requirements.txt
fi
```

The lock file is *always* present (it was committed as a placeholder), so CI
always installs from it — which means CI never exercises the unpinned
`requirements.txt` path and also never gets hash-verified packages.

**Action required (host with PyPI access):**
```bash
pip install "pip-tools>=7.4"
make lock   # pip-compile --strip-extras --generate-hashes ...
git add requirements.lock && git commit -m "chore: pin requirements.lock with hashes"
```

### 2.4 `.git/info/refs (2)` — Windows Explorer copy artifact (P3)

```
.git/info/refs (2)
```

A file with a literal space and `(2)` suffix in `.git/info/` — created by
Windows Explorer's "Copy" behavior when a file named `refs` already existed.
This file is outside git's expected layout and will confuse `git clone
--mirror` and `git remote update`.

**Action required:**
```powershell
Remove-Item ".git\info\refs (2)" -Force
```

### 2.6 `Makefile test` target uses `--maxfail=1` (P4)

```makefile
test:
    $(PYTHON) -m pytest -q --maxfail=1 ...
```

`--maxfail=1` stops the run after the first failing test. This is useful in
CI (fail fast), but for local `make test` it hides all subsequent failures.
When a developer is investigating multiple broken tests, they need to run
`pytest` directly. Consider either removing `--maxfail=1` from the Makefile
target or documenting this behaviour in `CONTRIBUTING.md`.

This is cosmetic; CI's explicit `pytest` invocation does not have `--maxfail=1`.
