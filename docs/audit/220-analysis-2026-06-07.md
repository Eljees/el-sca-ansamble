## 0. Суть проекта и текущие приоритеты

**el-sca-ansamble** — контейнерный SCA-комплекс для безопасности (Trivy, Grype, Syft,
cve-bin-tool) с Python-оркестрационным слоем (`resilient_updates`).

провенанс-отчётов, поддержка air-gap развёртывания через упакованные DB-бандлы.

**Текущая зрелость:** v0.1.0 выпущен 2026-06-06. 426 тестов, ruff clean, bandit 0 HIGH/MEDIUM.
Большинство первоначальных дефектов (D3–D18) закрыто.

## 4. Архитектурные проблемы

### 4.1 Множество точек входа — не консолидировано

| Скрипт | Назначение | Статус |
|---|---|---|
| `scripts/run-scan.sh` | Полный pipeline (362 LOC) | Основной POSIX runner |
| `scripts/scan_archive.sh` | Старый short runner (118 LOC) | Дублирует run-scan.sh |
| `scripts/run_scan.sh` | Per-tool wrapper (53 LOC) | Ещё один alias |
| `scripts/batch-scan.sh` | N кейсов | OK как батч-обёртка |
| `scripts/windows/run-scan.ps1` | PS-эквивалент | Основной Windows runner |
| `scripts/windows/batch-scan.ps1` | PS batch | OK |
| `resilient_updates/orchestrator.py` | Unified Python orchestrator | ✅ Новый (ADR-0005) |

`orchestrator.py` существует, но `cli scan` subcommand не выставлен как официальный
unified entrypoint — `scan_archive.sh` и `run_scan.sh` (без дефиса) создают confusion.

**Рекомендация:** пометить `scan_archive.sh` как deprecated в `scripts/README.md`,
убрать `run_scan.sh` (без дефиса) или свести к `exec ./run-scan.sh "$@"`.

### 4.2 `requirements.txt` — не pinned lockfile

Файл содержит loose constraints (`>=`) вместо хешированных pinned versions.
`pip-compile` ни разу не запускался. В CI каждый build тянет latest compatible.

**Риск:** тихий drift зависимостей. `PyYAML>=6.0` может стать `PyYAML==6.0.2`,
что сломает что-то в следующем minor release.

**Рекомендация:** `make lock` → `pip-compile --generate-hashes -o requirements.txt requirements.in`.
Требует PyPI доступ — задача для пользователя.

### 4.3 CI на GitHub Actions, репо на GitLab

Нет `.gitlab-ci.yml`. `.github/workflows/ci.yml` запускается только при push на GitHub.
Для реальной проверки качества нужен GitLab CI/CD.

**Приоритет:** P1 для производительности, но не блокирует функциональность.

### 4.4 D13 — Windows `_activate` race (carry-forward)

`cve_db_audit._activate` (строки ~353–365):
1. `shutil.copytree(active → previous)` — backup
2. `shutil.rmtree(active)` — **окно здесь**
3. `shutil.move(staging → active)` — окно закрывается

Для DB 6+ GB `shutil.move` по NTFS занимает секунды. Правильное решение —
`MoveFileExW(MOVEFILE_REPLACE_EXISTING)` через ctypes, или двухфазный
rename через `active.new`.

**Сложность:** высокая. Не трогать без отдельного Windows-тест-стенда.
