# CYBERSEC-13942: скан APK «вешал страницу» — разбор и фикс (2026-08-18)

## Исходная жалоба

> попытка просканить через http://10.2.108.47:8088/ артефакт отсюда
> w:\_dev_common\_SCA\CYBERSEC-13942\ вешает страницу и ничего не происходит

Артефакт: `android-build-iDocs-1332b1530-release-signed.apk` (Qt6/QML-приложение под Android, arm64-v8a).

Страница на самом деле не «висла» — под капотом было **пять независимых проблем**, которые накладывались друг на друга. Ниже — по порядку, как их находили и чинили.

---

## 1. Гонка параллельных сканов (архитектурная)

На сервере одновременно крутилось три скана (CYBERSEC-13702, CYBERSEC-13942, CYBERSEC-13329), все — через общие `artifacts/extracted/current`, `artifacts/sbom/`, `artifacts/reports/`. `start_scan`/`start_update` не имели взаимного исключения: скан PIX Studio (180 МБ) стартовал посреди прогона iDocs, его экстрактор подменил `extracted/current`, и отчёт с меткой «iDocs» вышел с компонентами PIX (818 вместо ожидаемых 135).

**Фикс:** `ScanBusyError` + `JobRegistry.active_job()` — второй `start_scan`/`start_update` во время активного джоба получает отказ, дашборд превращает это в HTTP 409 с понятным сообщением («уже выполняется..., дождитесь завершения»). Для upload-эндпоинта отдельно уточняется, что файл всё равно сохранён и его можно сканить с карточки позже.

Коммиты: `2a05f09` (фикс), `ac1a484` (тесты — JobRegistry-уровень и dashboard-уровень, 409).

## 2. Неудобства ручного запуска (не баг, но мешало диагностике)

- `run-scan.sh` использует `docker compose` и `python3 -m resilient_updates.cli` без явного `cd` — если запускать не из корня репо (`/home/SCA/el-sca-ansamble`), получаешь `no configuration file provided: not found`.
- Без `sudo` — `permission denied` на `/var/run/docker.sock`.

Оба нюанса не в коде, а в инструкции по ручному запуску — учтено при диагностике, отдельного фикса не требовало.

## 3. `find_apk()` никогда не находил standalone APK (реальный баг)

`docker-compose.yml` монтирует `${SCAN_TARGET_HOST}` прямо в `/scan-target` — путь внутри контейнера всегда без расширения. `find_apk()` в `scripts/analyze_apk.py` определял прямой APK-файл только по `path.suffix == ".apk"` — для `/scan-target` это условие никогда не выполняется. В результате **единственный сценарий, ради которого apk-analyzer существует** (один standalone `.apk`), всегда падал с `no .apk file found at /scan-target`.

**Фикс:** при пустом suffix — определять APK по содержимому (zip с `AndroidManifest.xml`/`classes.dex`, либо zip-обёртка с вложенным `.apk`).

Коммит: `0d206e8` + `tests/test_analyze_apk.py` (4 регресс-теста).

## 4. Найденное на 22 нативных Qt6-библиотеках: DB устарела? Нет.

После фикса №3 скан стал проходить (apk-analyzer/grype/cve-bin-tool — rc=0), но по всем 95 нативным `.so` (69 из них — Qt6, включая `libQt6Core`, `libQt6Gui` и т.д.) grype и cve-bin-tool находили **0 совпадений**. Проверила версии баз — обе свежие (grype 21.8ч, cve-bin-tool 15.8ч, вчерашнее обновление). Дело не в базах.

### 4a. У всех нативных компонентов `version: "unknown"`

`analyze_apk.py` собирал синтетический SBOM, где каждая `.so`-библиотека получала `version: "unknown"` и `purl: pkg:generic/<name>@unknown` — grype физически не с чем сравнивать диапазон уязвимых версий.

**Фикс:** не каждый Qt-модуль несёт в себе строку версии, но все Qt6-библиотеки одной сборки APK — из одного релиза Qt, так что достаточно найти строку `"Qt X.Y.Z"` один раз (надёжнее всего — в `libQt6Core`/`libQt6Gui`) и проставить найденную версию всем `libQt6*.so`-компонентам вместе с `cpe:2.3:a:qt:qt:<версия>:...` и `purl: pkg:generic/qt@<версия>`. На реальной поставке нашлась версия **Qt 6.10.2**.

Коммит: `1c70f23` + 4 новых теста в `tests/test_analyze_apk.py`.

### 4b. CPE терялся на полпути к grype (второй, более тонкий баг)

grype не сканирует `syft.json` напрямую — он читает `artifacts/sbom/scan-input.cdx.json`, который собирает `resilient_updates/sbom_ingest.py` (конвертация syft → CycloneDX). Функция `_components_from_syft()` копировала только `name`/`version`/`purl` — поле `cpes` **молча терялось**. То есть даже после фикса 4a, с правильной версией `6.10.2`, CPE до grype не доезжал, и находок всё равно было 0.

**Фикс:** копировать первый CPE из списка `cpes` (syft) в поле `cpe` (CycloneDX — там оно одиночное, не список).

Коммит: `3a388be` + тест на прохождение CPE через весь конвейер.

### Итоговая проверка (грипп-санити)

После обоих фиксов CPE действительно доезжает до `scan-input.cdx.json` — проверено напрямую. На реальной версии **Qt 6.10.2** совпадений всё ещё 0 — но это уже не баг: прогнала тот же самый grype (тот же образ, тот же кэш БД, тот же формат CPE) на заведомо старой уязвимой версии **Qt 5.6.0** — нашлось **25 CVE** (включая Critical/High: CVE-2017-10904, CVE-2018-19870 и др.). Значит конвейер сопоставления работает корректно; для Qt 6.10.2 в текущей базе grype просто нет известных уязвимостей (либо версия слишком свежая для фида).

## Что осталось за скобками (не чинила, для информации)

- **cve-bin-tool** не находит Qt в принципе — в его списке чекеров (`--list-checkers`, всего 33 в этой версии образа) Qt-чекера нет. Это ограничение инструмента, не БД: сколько её ни обновляй, cve-bin-tool не научится опознавать Qt в бинарнике.
- **Не-Qt нативные библиотеки** (26 из 95: `libcrypto_3.so`, `libc++_shared.so`, `libcspjni.so`, `libiDocs_arm64-v8a.so` и др.) по-прежнему `version: unknown` — версию из них не тащили, это отдельная задача при желании (для каждой библиотеки нужен свой паттерн опознавания версии).
- **GitHub** (`origin`) снова отстаёт от GitLab/сервера — прежний PAT протух второй раз за сессию. GitLab и сервер (`10.2.108.47`) на актуальном коммите `3a388be`, GitHub — нет. Нужно запушить вручную свежим токеном.
